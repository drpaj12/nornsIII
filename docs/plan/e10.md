# E10: algorithm parameter sweep (Stage 0 pre-registration, written 2026-10-28 before the first sweep run)

Purpose (hub docs/purpose.md, Mimir **Mi Q2.3**): which algorithm parameters change the mapping of a structure class, and how much result quality (area, speed) follows from that.
Peter 2026-10-27: yes to E10 (controller brief `mimir-e10-sweep.md`, roadmap E10). Data first (Peter 2026-10-26): collect, store, tabulate; no hypotheses beyond the pre-registered comparisons of Section 6.
Measures per run: LUTs, CLBs (area), critical path delay CPD (speed), routed wirelength WL, minimum channel width W, runtime; per structure class the downstream form (Mimir `structure_mapping`).
This file is committed and pushed before any sweep run; its commit time is the pre-registration time. A rule changes only by a NEW dated entry at the end that keeps the old rule.
The only runs before this commit are the netlist builds of Section 2 (needed to order the designs) and the 3-design gate of Section 7, labelled `e10gate` in every record; the gate is not sweep data.

Base facts, each cited:
* **Odin III:** main checkout at commit b01a8034 (clean tree), built out of tree with `cmake -S odin3 -B <tmp> -DCMAKE_BUILD_TYPE=Release`; `odin3 --version` prints 1.2.0 and no commit, so the commit is recorded `given` only when the tree is clean, the build directory was configured from it and the binary is newer than HEAD (all three checked at run time and stored in the record). The built-in default ABC script is `lib/abc/vtr.abc` of that commit (lines 1-10; `docs/DESIGN.md` line 225: it applies when no `--script`, `--abc-script` or project script is given). Odin III script for a Verilog design: `read_arch ARCH; read_verilog --nolatches --vtr-compat --prov-ast refs F; proc; fsm; opt; flatten; opt -full; wreduce; hardmap; lower; abc [--script S] --lut K; stats; write_blif --vtr --lut-k K --name-style hash --prov-map OUT`, with `--top` the module `find_top` gives (the module no other module instantiates; the last when several; Mimir `structbatch.find_top`). The hash-named BLIF and the version 2 name map are what Mimir's structure rows need.
* **VPR:** Norns build `$NORNS_VPR` (VTR 3c9a4d23b2 plus the Norns packer overlay, checked per record). Flags of every VPR run: `--seed s --timing_report_npaths 200 --route_file /dev/null --write_flat_place F`, the minimum-channel-width search (no `--route_chan_width`), as placers_main.py. Everything else is VPR's default.
* **Unrelated clustering:** the VPR default is `auto` (`vpr/src/base/read_options.cpp:2443-2451`, "Dynamically enabled/disabled (based on density)"), so neither `on` nor `off` is the default and both are run. The base is `auto`.
* **Architecture files** (read only under `$VTR_ROOT/vtr_flow/arch/timing/`): base `k6_frac_N10_frac_chain_mem32K_40nm.xml` (the file Norns uses; K=6 fracturable LUTs, N=10, carry chains, 32 Kb memories, multipliers); (b) K4 file `k4_N4_90nm.xml` (the plain K=4, N=4 VTR architecture, the one `qor_legs.ARCH_BASES["k4"]` of odin3 names); (c) `EArch.xml` (K=6 with lut4/lut5/lut6, adder, multiplier and memory blocks).
* **Confounds stated, not removed:** `k4_N4_90nm.xml` has no memory, multiplier or carry-chain blocks (its pb_types are `lut4`, `ff`, `inpad`, `outpad`), so for designs with such blocks the K=4 level also changes whether they stay hard blocks (Odin III `hardmap` maps what the architecture lacks to soft logic). EArch differs from the base file in more than the name. Both are one *architecture* change, not one parameter. The comparisons say so in their captions.

### 1.1 The two alternative ABC scripts (chosen from the Odin III docs before any run)
* **abc1**: VTR's old ABC stage (`use_old_abc_script`: `resyn; resyn2; if -K K; scleanup`), odin3 `docs/PHASE3.md` Section 10, decision 10 option (b). Two changes were needed and are checked: `strash` in front (the `resyn` aliases need an AIG; without it ABC aborts), and `scleanup` before `if` (after the mapping ABC aborts in this build; checked on `s298`). Why: it is the other script the Odin III authors name for VTR, it optimises by rewriting (`resyn`, `resyn2`) instead of `dch` choices, so it tests whether the optimisation recipe changes the mapping of a structure class.
* **abc2**: the default script with one change, `if -a -K K -v` (area-oriented LUT mapping; `docs/user/outputs.md` lines 54-55: `if` maps for delay unless `-a`). Why: one-parameter change of the mapper objective, area against delay.

## 2. Run records and tables
* Every run writes `mimir-run.json` through `scripts/runrecord.py` (all fields given or cited default; the VPR commit by the overlay rule), plus a shared `odin3` step with the Odin III command, its tool entry and parameters (`odin.abc_script`, `odin.abc_script_sha256`, `odin.lut_k`, `odin.arch_file`, `odin.script`, `odin.input_kind`). Run root `runs-e10/` (not committed); the source label of a record is `norns-placers-e10-<config>`.
* Import into `work/mimir-data/e10.db` with `mimir import-runrecords` (`MIMIR_HOST_MAP`), then structure rows with `mimir.structnorns` (branch `exp/e10` of mimirIII; adds `structure`, `structure_member` and `structure_mapping` rows for a run that already has a run record, with the run's id; the HDL structure ids are shared by the runs of a design, slug `e10/<design>`).
* Per run, before the structure rows: `odin3 tools/flow/prov_post.py` on a private copy of the name map with that run's own `.net` and `.place` (packing and placement levels).
* `mimir privacy-check` on `e10.db` and the run records: 0 hits required.

## 3. Measures
Per run: LUTs (`.names` with at least one input of the netlist), CLBs (`blocks of type: clb` of the VPR log), CPD (`Final critical path delay (least slack)`), WL (`Total wirelength`), W (`Best routing used a channel width factor`), runtime (the VPR flow seconds; for the external arms also the nextpnr seconds, reported separately). Summary tables are written by `scripts/e10_tables.py` into `data/e10/` (CSV and JSON); every number in Section 8 has its caption.

## 4. Stop rules
1. A config failing (rc not 0, not legal-routed, or no netlist) on more than 20% of the designs: stop that config and report (checked after each design once at least 5 designs ran).
2. Any `structure_mapping` row without a run record in `e10.db`: stop.
3. Memory: total RSS of running processes at most 14 GB (60% of the VM); `free -g` before each batch. One VPR at a time (the Norns lock), so the sweep itself stays far below.
4. `/mnt/c` free space under 30 GB: stop before the next design.
5. A failed run is retried once (placers.md Section 5 rule 4); the first failure is kept in the data.
6. Anything that would need a deletion, a change to `$VTR_ROOT`, an external clone or another lane's `runs/`: stop.

## 5. Concurrency and locks
VPR runs and long nextpnr runs hold `/tmp/claude-1000/norns-vpr.lock` as placers_main.py does; Odin III builds (one, done) went through `tools/build-locked`. Runs are sequential (the lock allows one VPR); structure steps run after each design. Page-cache eviction after each design with the lane's `evict.py`.

## 6. Pre-registered comparisons
For each factor level L (a config other than `base`, and each placer arm of `plc` taken as its own level) and each measure M in LUTs, CLBs, CPD, WL (W and runtime are shown in the tables, not in the pre-registered comparison):
* per design d: the median over seeds 1-3 of M in L (successful seeds only) divided by the median over seeds 1-3 of M in the base (`vpr_sa` of `base`); LUTs have one value per netlist;
* the geometric mean of that ratio over the designs with a value in both L and base, with a 95% percentile bootstrap interval, designs resampled with replacement, 10,000 resamples, seed 20261026;
* reported for all 35 designs, and for MCNC 20 and Norns 15 separately; n designs printed beside every geomean. A design with no successful run in L or in base is excluded from that level and listed.
Per structure class (the `structure.kind` vocabulary of Mimir; Norns 15 only): the **share of instances whose downstream form differs from the base run** of the same design and seed. An instance is a `structure` row of the design that has a `lut` mapping row in the base run; its form in a run is the tuple (`lut` row: `n_luts`, `n_ffs`, `n_carry`, `n_pure`, `lost_at_pass`; `ble` row: `n_bles`; `clb` row: `n_clbs`), a missing row counting as `none`. The structure differs when the form tuple differs from the base run's (same design, same seed; placed-level coordinates are not part of the form). Reported per config and kind with the counts (differing / instances); for `plc` the base is the `vpr_sa` run of the same seed. Rows with fewer than 5 instances are marked.
Everything else computed from the data (other measures, other groupings, rank correlations) is labelled **exploratory**.

## 7. Gate (labelled `e10gate`) and the estimate
Gate: the smallest three designs by the order above (stereovision3, ch_intrinsics, diffeq2), all 8 configs, seeds 1-3: **90 runs, 90 ok, 0 failed**, wall time **161 s** for the runs plus 21 s for the structure steps and run-record import into a scratch store (30 flow configurations, all `full`; every `structure_mapping` row joined to a run row). The gate runs are kept in `runs-e10/` under the label `e10gate` and are not part of any comparison.
**Run count (final VPR runs):** 35 designs x 3 seeds x (`base` 1 + `abc1` 1 + `abc2` 1 + `k4` 1 + `earch` 1 + `uon` 1 + `uoff` 1 + `plc` 3 arms) = **1,050 runs**, plus the shared `vpr_ap` seed-1 reference of `plc` (it is one of the `vpr_ap` runs), plus retries; 175 Odin III runs (5 netlists x 35 designs); 105 x 2 nextpnr runs (+35 probe runs) for the external arms.
**Wall time estimate:** the sweep is serial (one VPR). Scaling the 15 Norns designs by the per-run seconds of the placers main comparison (Section 10.9 data, `vpr_sa` means over seeds 1-3: about 314 s per seed over the 15 designs, 174 s of it `stereovision2`) gives about 3 hours for the Norns 15; the MCNC 20 (smaller on average, a few with 2,000 to 2,800 LUTs) are estimated at 2 to 3 hours; the structure steps at 20 s per 90 runs for the smallest designs and more for the large ones. **Total estimate: 6 to 9 hours**, to be replaced by the measured time in Section 8.

## 9. Dated entry 2026-10-28 (during the first sweep batch, before any `k4` result was used): time limit for the `k4` config
First batch, design 10 (`boundtop`): the `k4` run (seed 1) was still routing after 40 minutes (the VPR log showed 9,948 CLBs against 54 in the base: `k4_N4_90nm.xml` has no memory or multiplier blocks, so Odin III maps the design's memory and multipliers to soft logic; the confound named in Section 1). It was stopped by hand; its work directory stays in `runs-e10/vpr/e10-k4/boundtop` and is overwritten by the re-run. This follows from Section 1, not a surprise about the method, but the 7,200 s run timeout of placers.md Section 5 would let each such design cost up to 12 hours (three seeds, one retry).
New rule, for the `k4` config only (the old rule stays for every other config): one VPR run is limited to **900 s** (`timeout` inside the lock; recorded with exit code 124); it is not retried; the remaining seeds of that design are skipped and listed; the design counts as failed for stop rule 1. Stop rule 1 stops a config for the rest of the sweep (the sweep driver writes `stopped-configs.json` and continues with the other configs); the runs already made stay in the data and the report names the config and the design after which it stopped. Chosen by the lane as an agent default; Peter may override it.
