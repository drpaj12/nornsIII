# The Norns III

**Status: closed (negative results), 2026-10-31.** See `docs/plan/STATUS.md` for the experiments, archive locations and how to reopen.

The Norns III is the placement experiment of Yggdrasil III (hub: <https://github.com/drpaj12/YggdrasilIII>): does keeping the
designer's grouping (the Odin III provenance hierarchy) or a recovered clustering (Loki III L2), or any other cheap change to
packing and placement, buy a deployable gain in speed, wire or area on VPR (VTR 9)? The answer is no. Stages: a known-optimum
yardstick that measures the room left; an instrumented packer (VPR's AAPack/APPack at a pinned commit with a provenance-affinity
term); seeding of VPR's anneal from a clustering, with a crossover sweep; gap anatomy and heap studies; and a set of tried changes
(HDL-aware packing, refreshed criticality, seed rule, two-hop gain, spare room, duplication after placement), none of which beat noise.

Headline (paper, `docs/paper/norns.tex`, built PDF `docs/paper/build/norns.pdf`): the standard packer uses 22% more wire than the
known grouping over all topologies and 49% more on meshes and trees; on 33 real designs made into known-optimum yardsticks it
needs 1.103 times the proven lower bound on CLBs and 1.265 times the wire of the known grouping (delay inconclusive). 60% of
the CLB gap is in one kind of pick: an atom of another cluster taken while the right one was queued. An HDL-aware packer first
showed a 0.902 wirelength ratio, which was a leak; with realistic registers it used 65% to 150% more wire. The other tried changes
gave a geomean speed change between -2.1% and +0.7%. What remains useful is the yardstick and the instruments.

## Limitations of the Norns packer (measured 2026-10-25, not fixed)

The proposal step (up to 30 unclustered members of a cluster's dominant group handed to the candidate queue) counts molecules
handed over, not molecules the queue accepted, and scans the group from the lowest atom id (netlist-order bias). A log-only counter
(packing unchanged: `.net` byte-identical to the previous binary on 45 of 45 headline configurations) gives, over the 15 designs,
medians of the queued share of handed-over molecules 49% / 46% / 48% and of proposal calls that queued nothing 13% / 55% / 49%
(module / word / word+io). Per design (queued share / calls with nothing queued; headline beta 4, seed 1):

| design | module | word | word+io |
|---|---|---|---|
| blob_merge | 92% / 0% | 5% / 99% | 13% / 97% |
| boundtop | 44% / 16% | 63% / 49% | 64% / 48% |
| ch_intrinsics | 82% / 1% | 87% / 20% | 87% / 20% |
| diffeq1 | 53% / 7% | 59% / 28% | 59% / 28% |
| diffeq2 | 63% / 6% | 75% / 20% | 75% / 22% |
| mkDelayWorker32B | 8% / 60% | 0% / 100% | 0% / 100% |
| mkPktMerge | 22% / 58% | 24% / 57% | 24% / 57% |
| mkSMAdapter4B | 22% / 20% | 50% / 55% | 48% / 47% |
| or1200 | 29% / 22% | 46% / 52% | 42% / 49% |
| raygentop | 49% / 13% | 43% / 60% | 38% / 60% |
| sha | 88% / 4% | 46% / 62% | 48% / 57% |
| stereovision0 | 80% / 7% | 78% / 68% | 78% / 68% |
| stereovision1 | 34% / 41% | 78% / 44% | 76% / 44% |
| stereovision2 | 17% / 57% | 46% / 37% | 46% / 37% |
| stereovision3 | 66% / 5% | 12% / 84% | 12% / 84% |

The fix (count queued molecules only, return a bool, scan order) is queued for round 4. Affinity-file entries that did not match
an atom are listed per design and source in `data/analysis/r3fix-match.json` (for example mkDelayWorker32B matches 38 of 1620 word entries).

Which round-four steps need what. Only `scripts/write_round4.py` (and `write_round3.py`) regenerate byte-identically from a plain
`git archive` of this repository (they read the committed `data/`, `data/analysis/r4-*.json` and `docs/plan/round4.md`). Everything
upstream of `data/` needs `runs/` (not committed): `round4.py` (all modes; the VTR build `$NORNS_VPR`, the stock `vpr`, and for gate
(c) the round-3 binary `$NORNS_VPR_R3`, built by `sh packer/build.sh --r3`), `r4census.py`, `r4near.py` and `r4hier.py`
(BLIFs and run directories under `runs/<d>/`; `r4hier.py` also runs the Odin III build in `$ODIN3_ROOT` for the pre-flatten
hierarchy), `r4depth.py` (`runs/<d>/r4/stock.analytic.s1/attr.json` and the benchmark Verilog under `$VTR_ROOT`, whose paths the
attribution records), and `r4stats.py` (the committed `data/<d>/` records, plus `runs/` for K6 (round-3 `vpr.out`), K7
(`paths.json.gz`, `final.flat_place`) and the CPD and coverage checks (`paths.json.gz`)). `data/analysis/r4-results.json` is
therefore reproduced only where `runs/` exists.
